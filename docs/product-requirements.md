# 产品需求

## 产品目标

Forge 要让用户提交一条产品式需求，然后得到一次被系统化调度的软件开发流程。它不应该像普通聊天机器人，而应该像一个有角色、有流程、有状态、有交付物的小型 AI 开发团队。

核心用户故事：

> 作为一个前端开发者，我希望描述一次功能需求后，Forge 能自动协调规划、分工、实现、验证和打包，这样我就不用反复手动提示多个 AI 工具。

## 目标用户

| 用户 | 需求 |
| --- | --- |
| 想进入 AI/全栈领域的前端开发者 | 希望获得全栈交付能力，但不想手动扮演后端、测试、运维、产品经理 |
| 独立开发者 | 希望 AI 可以长时间自动推进，并留下可审阅产物 |
| AI 重度工程团队 | 希望 AI 工作流可复用、规则可共享、聊天上下文不再散乱 |

## 核心承诺

一条指令应该变成这样一条链路：

```text
客户式需求
  -> 任务接收
  -> 需求和架构规划
  -> 按角色拆分工作
  -> 多模型并行执行
  -> 集成产物
  -> 检查和自修复
  -> 最终交付包 + 警告 + 下一步
```

## MVP 能力

1. **从一条指令创建任务**
   - 保存原始需求、推断目标、约束和预期交付物。
   - 在任何实现工作开始前，先把任务文件落盘。

2. **先规划，再实现**
   - Architect 角色负责拆解需求。
   - 如果规划输出缺失或无效，Forge 使用确定性兜底计划继续推进。

3. **运行多角色线程**
   - 依赖关系允许时，frontend、backend、tester、devops 可以并行工作。
   - 每个角色都要写出明确产物和状态。

4. **检查和自修复**
   - Tester / check 阶段先审查生成结果，并尽量自修复。
   - 当交付物已经存在时，验证失败不一定代表整个流程失败。

5. **生成最终交付包**
   - 输出最终摘要、产物列表、执行过的命令、警告和剩余风险。
   - `completed_with_warnings` 是一等结果状态。

## MVP 不做什么

- 不做完整编辑器替代品。
- 不做全自动生产部署。
- 不承诺不经人工审查就得到完美正确代码。
- 不做复杂企业权限系统。
- 本地工作流稳定之前，不优先做实时多设备同步。

## 成功标准

Forge MVP 成功的标志：

- 一个非平凡全栈 demo 可以无人值守跑数小时，不会因为一次模型输出格式错误卡死。
- 用户可以在磁盘上检查每个关键决策和产物。
- TUI 清楚展示哪个 Agent 正在运行、阻塞、失败或完成。
- 系统能说明某个结果来自主模型、修复后的输出、缓存，还是确定性兜底。
- 某个模型调用失败不会导致整个工作流归零。

## 产品约束

- 第一贡献者画像是 TypeScript / JavaScript 开发者。
- Go 用在有明显运行时价值的地方：并发、daemon、本地 API、持久编排。
- TypeScript 用在有明显贡献体验价值的地方：CLI、TUI、插件、UI 组件。
- 每个长流程都必须在中途失败时产生部分价值。
